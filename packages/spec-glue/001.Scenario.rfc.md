# Scenario API

## Summary
This RFC proposes the unification of different `Scenario` representations (`ScenarioInstance` and `ExecutableScenario` interfaces) in the codebase. This simplifies scenario management, registers a unified state, and avoids confusion.

## Motivation
There are currently different `Scenario` representations or related structs in code that may cause confusion on the expected behavior. For this reason we want to merge the `ScenarioInstance` and `ExecutableScenario` interfaces.

Prior to these changes, the original structures in the codebase at commit `a6e510be145ff5c69c2e95fda0bf4bd1591aaff2` were separated in:
- `src/create-feature.d.ts` (Types definition file)
- `src/create-feature.ts` (Implementation file)

At that snapshot, calling `Scenario(...)` during feature definition returned a `ScenarioInstance`, while the factory returned a Map of `ExecutableScenario` instances, each instantiating its own `Store` inside the `run` method execution.

## Detailed Design

We merged `ScenarioInstance` and `ExecutableScenario` into a single, unified `Scenario` interface.

Additionally:
1. To avoid race conditions and ensure store readiness, the isolated `store: Store` is now instantiated eagerly when the Scenario is created rather than dynamically during execution inside `.run()`.
2. The `.configure(...)` method has been improved to support polymorphic signatures (either a complete/partial configuration object or a modifier callback function), and returns `Scenario` (the Scenario instance itself) to allow fluent method chaining.

The unified interface is:

```ts
export interface Scenario {
  /** The deterministic slug or explicitly provided identifier. */
  readonly id: string;
  /** The cleaned title of the scenario, stripped of tags. */
  readonly title: string;
  /** Extracted metadata tags (e.g., ['smoke', 'e2e']). */
  readonly tags: string[];
  /** The isolated store initialized for the execution of this scenario. */
  readonly store: Store;
  /** Merges new configuration values into the current scenario scope. */
  configure: (configModifier: Partial<FeatureConfig> | ((prev: FeatureConfig) => FeatureConfig)) => Scenario;
  /** Registers a step specifically within the scope of this Scenario. */
  Step: StepRegistrationFn;
  /**
   * Triggers the evaluation of this specific scenario's steps.
   * 
   * **Execution Note:** Calling `.run()` isolates execution to this specific AST node.
   * This targeted dispatch prevents the infinite loops associated with self-referential
   * monolithic `execute()` loops in meta-testing.
   */
  run: () => Promise<void>;
}
```

This interface is now used as both the return type of `Scenario(...)` registration, and the value type in the `scenarios` Map exposed in `FeatureInstance`.

### Concrete Files Affected
- **`src/create-feature.d.ts`** (Unified the interfaces, updated `FeatureInstance.scenarios` and `ScenarioRegistration` to refer to `Scenario` instead of `ExecutableScenario` and `ScenarioInstance`, and updated the `configure` method signature).
- **`src/create-feature.ts`** (Created `ScenarioImpl` which implements the unified `Scenario` interface, instantiates `StoreImpl` eagerly in the constructor, merges config on `configure`, supports fluent chaining, and updated the factory function `createFeature`).

## Drawbacks
- Late Mutation Hazard: Overwriting configuration via `.configure(...)` after steps are registered could lead to unexpected behavior if run concurrently.
- Late mutation Hazard of the store in the middle of execution if the same scenario is run multiple times concurrently.

## Rationale and alternatives
We can omit the store or instantiate a fresh store on each run to avoid side-effects across repeated runs of the same scenario instance. However, eager initialization satisfies the requirement of having a pre-existing store ready before execution.
